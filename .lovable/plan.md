

## Proactive Mastery Plan — Time-of-Day Logic Audit

### The Two Bugs You Spotted

**Bug A: "Check in to personalise your evening plan" showing in the morning**

The screenshot shows "Morning, Shukrita" (correct greeting) but the mastery plan section shows "Evening Close" with an "Evening" pill. The check-in prompt says: *"Check in to personalize your evening plan"* — but it's morning.

**Root cause:** The `generate-mastery-plan` EF uses `getTimeOfDay(timezoneOffset)` to compute the period. The `timezoneOffset` comes from the client via `new Date().getTimezoneOffset()`. If the compute-outer-readiness EF was called server-to-server (line 1090 of generate-mastery-plan) WITHOUT forwarding the client's timezoneOffset, it defaults to `timezoneOffset = 0` (UTC). At midnight UTC (which is morning in BST/IST), this would return "evening" because UTC hour 0 maps to evening in the `getTimeOfDay` function (anything outside 5-17 = evening).

Looking at lines 1086-1106, the server-to-server call to `compute-outer-readiness` sends `{ userId: req.userId }` — it does NOT pass `timezoneOffset`. So compute-outer-readiness uses the default `timezoneOffset = 0`, computing the theme using UTC time, which can be a different time of day than the user's local time.

However, the main `getTimeOfDay` call on line 911 DOES use the client's timezoneOffset. So the period (morning/afternoon/evening) in the plan response should be correct. The fact that the screenshot shows "Evening Close" means either:
1. The timezoneOffset was wrong when sent, OR
2. A cached plan from a previous evening session is being served (rate limiting cache on line 1477 returns old response within 30s), OR
3. The session cache (`sessionStorage`) from a previous evening is persisting

**Actually** — looking more carefully at the screenshot: the greeting says "Morning" but the mastery plan shows "Evening Close". This is a clear mismatch. The most likely cause is **session caching**: the plan was generated during the evening and cached in sessionStorage. The cache key is `plan-loaded-${todayDate}-${currentPeriod}` (line 229). Since `currentPeriod` is derived client-side via `getCurrentTimeWindow()` which uses `new Date().getHours()`, the morning session should have a DIFFERENT key. But if the user opened the app at midnight (which is "evening" by the app's definition: hour >= 17), the plan would be evening, and it would persist.

Wait — midnight (hour 0) is NOT >= 17, so `getCurrentTimeWindow` would return "morning" (hour >= 5 is false for 0, so it falls to evening since < 5 and >= 0, but actually the function is: `if (hour >= 5 && hour < 12) return 'morning'; if (hour >= 12 && hour < 18) return 'afternoon'; return 'evening';` — so hour 0 returns "evening"). 

**The real issue:** The time windows don't align. Hours 0-4 are "evening" in `getCurrentTimeWindow` but the user sees it as very late night/early morning. The greeting function uses `hour < 12` for "Morning". So at midnight (hour 0), the greeting says "Morning" but the plan says "Evening". This is the exact bug.

**Bug B: Outer Readiness Brief showing evening themes in the morning**

"Let the day close" is generated by `compute-outer-readiness` when:
- `tier === 'depleted'` AND `lateEvening` (hour >= 21 or hour < 6) in the no-calendar path, OR
- `tier === 'depleted'` AND `timeOfDay === 'evening'` in the calendar path

Same root cause — if `timezoneOffset` is 0 or the user opened the app between midnight-5am local time, the outer readiness computes as evening/late-evening.

### Full Time-of-Day Logic Flow

```text
CLIENT SIDE:
  getCurrentTimeWindow() [dailyCheckins.ts]:
    hour >= 5 && < 12 → morning
    hour >= 12 && < 18 → afternoon
    else → evening  (includes 0-4am AND 18-23)

  getGreeting() [ExecutiveHome.tsx]:
    hour < 12 → "Morning"
    hour < 18 → "Afternoon"  
    else → "Evening"

  ⚠️ MISMATCH: 0-4am → greeting="Morning" but timeWindow="evening"

SERVER SIDE:
  getTimeOfDay() [generate-mastery-plan]:
    localHour >= 5 && < 12 → morning
    localHour >= 12 && < 17 → afternoon
    else → evening

  ⚠️ MISMATCH: 17:00 → server="evening" but client getCurrentTimeWindow="afternoon" (< 18)

  getTimeOfDay() [compute-outer-readiness]:
    hour >= 6 && < 12 → morning (⚠️ uses 6 not 5!)
    hour >= 12 && < 18 → afternoon (⚠️ uses 18 not 17!)
    else → evening

  isLateEvening() [compute-outer-readiness]:
    hour >= 21 || hour < 6 → true
```

### Summary of Issues to Fix (for future session)

| Issue | Severity | Detail |
|-------|----------|--------|
| **0-4am returns "evening" but greeting says "Morning"** | Critical | `getCurrentTimeWindow` returns evening for hours 0-4, but greeting logic treats hour < 12 as "Morning". User sees contradictory messages. |
| **Morning boundary inconsistency (5 vs 6)** | Medium | `generate-mastery-plan` uses 5am, `compute-outer-readiness` uses 6am as morning start. |
| **Afternoon boundary inconsistency (17 vs 18)** | Medium | `generate-mastery-plan` ends afternoon at 17, `compute-outer-readiness` at 18, client at 18. Plan could say "evening" while client thinks it's "afternoon". |
| **Outer readiness server-to-server call missing timezoneOffset** | Medium | Line 1096 of generate-mastery-plan doesn't forward `timezoneOffset` to compute-outer-readiness. The EF defaults to UTC (offset=0). |
| **Rate limit cache not period-aware** | Low | The 30s rate limit cache (line 1477) doesn't account for period changes. If user calls at 17:59 and again at 18:01, they get the old afternoon plan. |

### Recommended Fix Approach (when ready)

1. **Standardize time windows** across all 4 locations to one canonical set: morning 5-12, afternoon 12-18, evening 18-5 (or 17-5)
2. **Forward timezoneOffset** in the server-to-server outer readiness call
3. **Align greeting logic** with time window logic (0-4am should say "Evening" if the plan says evening, OR the plan should say "morning" if the greeting says "Morning")
4. **Make rate limit cache key include period** to prevent stale cross-period responses
